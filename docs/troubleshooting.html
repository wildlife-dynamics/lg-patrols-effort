Troubleshooting

Common issues encountered while configuring, running, or contributing to the LG Patrols Effort Workflow, and how to resolve them. If your issue isn't listed here, open an issue on GitHub.

Configuration & EarthRanger Connection

Study area layers (Conservancies, Group Ranch Boundaries) are missing from every map

These layers are not bundled with the workflow — they are fetched live via get_spatial_features, querying the Conservancies and Group Ranch Boundaries feature types on the connected EarthRanger instance. If either feature type does not exist (or is named differently) on your instance, that layer is silently absent from the composited maps rather than raising an error.

No patrols or events are returned

By default, Patrol Types is restricted to routine_patrol and, under Advanced Configurations, patrol status is restricted to done. If your EarthRanger instance records other patrol types or statuses, clear or expand these filters.

Events near the edge of the ecosystem are missing

The Filter Patrol Events bounding box is pre-filled to the Amboseli ecosystem extent by default. Events outside that box are excluded even if they fall within the selected time range. Clear the bounding box to include all events regardless of location.

Patrol Trajectories map shows every track the same colour

This is expected — unlike the Patrol Events map (which colours points by event_type), the Patrol Trajectories map always renders tracks in a single fixed colour (#008b8b). There is no user-selectable colour category for this map in the current workflow version.

A patrol track segment is missing even though the patrol appears in the events map

Trajectory segments are dropped by the segment filter if they're shorter than 10 m or 10 s, longer than 100 km or 6 hours, or average slower than 1 km/h or faster than 7 km/h (the 7 km/h ceiling assumes foot patrols — a genuinely fast foot segment can be excluded). A daytime filter also drops any fix recorded outside 06:00–19:00 local time.

Reports & Dashboard

Can't find a patrol-type breakdown CSV in the output directory

A patrol-type summary (summarized_patrol_types) is computed internally but its result is never persisted to a CSV or wired into the Word report or dashboard — this is a gap in the current spec.yaml, not a run failure. If you need this breakdown, use the Patrol Type grouper instead, which produces a full per-type set of outputs.

Word report is missing images or fails to render

render_docx_page runs with strict_images: true, so a missing PNG for any group (e.g. because that group's map/chart was skipped due to an empty DataFrame) will raise an error rather than silently leaving a blank box.

No outputs written / can't find results

All outputs are written to the directory specified by the ECOSCOPE_WORKFLOWS_RESULTS environment variable. Confirm it's set and points to a directory the workflow process can write to.

Contributing & CI

These apply if you're modifying the workflow itself (spec.yaml, test-cases.yaml, or the generated ecoscope-workflows-patrols-workflow/ directory) and opening a pull request.

Generated files differ from committed files in ecoscope-workflows-patrols-workflow

The generated workflow directory is out of sync with spec.yaml. Run the recompile script locally and commit the result:

pixi run --manifest-path pixi.toml --locked bash -c "./dev/recompile.sh --update"

Found wildcard version (*) in requirements or Found local file channel (file://) in requirements

In spec.yaml, every dependency under requirements must pin an exact version (or version range) and use a remote conda channel — wildcard versions and local file:// channels are only valid for local development, not for CI using published packages. This workflow already runs on the consolidated ecoscope-platform package — don't reintroduce the older ecoscope-workflows-core/ecoscope-workflows-ext-ecoscope split when editing it.

VERSION.yaml (...) must be greater than main branch (...)

Bump MAJ/MIN/PATCH in ecoscope-workflows-patrols-workflow/VERSION.yaml so it's strictly greater than the version on main before opening or updating a PR.

test-cases.yaml must contain at least one test case

Every workflow requires at least one top-level entry in test-cases.yaml with a params block. See the existing entries in that file for the expected format.

Workflow tests fail in CI but pass locally (or vice versa)

test.yml runs test cases against all of ubuntu-latest, macos-latest, and windows-latest. Since this workflow depends on a live EarthRanger connection and Dropbox downloads (Word templates, org logo), a CI-only failure is more likely to come from those external services being unreachable or rate-limited than from OS-specific behaviour.
